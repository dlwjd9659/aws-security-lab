## 표준이 다르면 결과가 다르다

같은 Security Hub, 같은 리소스인데 두 표준의 결과가 거의 겹치지 않는다.

| | CIS v1.2.0 | FSBP v1.0.0 |
| --- | --- | --- |
| 실패 컨트롤 | 29 | 48 |
| 심은 취약점을 잡은 수 | 1.5 / 13 | 10 / 13 |
| 주된 점검 영역 | IAM 정책, 로그 설정, CloudWatch 경보 | 개별 리소스 설정 |
| 보안 그룹 점검 포트 | 22, 3389 만 | 고위험 포트 전반 (3306 포함) |

CIS v1.2.0 은 2018 년 기준이라 계정 수준 통제에 치우쳐 있다.
S3 퍼블릭 차단, RDS 암호화, IMDSv2 같은 리소스 설정 항목이 아예 없다.

**"CSPM 을 켰다" 는 말에는 정보가 없다.** 어떤 표준을 켰는지가 탐지 범위를
결정한다. CIS 만 켠 환경에서는 퍼블릭 S3 버킷이 그대로 통과한다.

## 예측이 틀린 두 항목

### 13 번 — 설계 판단인 줄 알았는데 규칙이 있었다

"퍼블릭 서브넷에 DB 를 두는 것은 설계 의도에 따라 달라지므로 위반으로
판정하기 어렵다" 고 예측했다. 틀렸다.

`RDS.46 — RDS DB instances should not be deployed in public subnets with
routes to internet gateways` 가 정확히 이 구성을 잡는다.
라우팅 테이블에 인터넷 게이트웨이 경로가 있는 서브넷인지까지 판별한다.

`EC2.9`(퍼블릭 IPv4 주소 보유), `EC2.15`(서브넷이 퍼블릭 IP 자동 할당)도
같은 구조를 다른 각도에서 지적한다.

**배운 것**: 판단이 필요해 보이는 항목도 조건을 충분히 좁히면 규칙이 된다.
"자동화할 수 없다" 는 추측은 기준을 직접 확인하기 전에는 하지 않는다.

### 5 번 — 부분적으로라도 잡힐 줄 알았다

EC2 인스턴스 역할에 `AmazonS3FullAccess` 와 `AmazonBedrockFullAccess` 가
붙어 있다. CIS 도 FSBP 도 이에 대해 아무 말을 하지 않는다.

CSPM 은 "권한이 설정되어 있는가" 는 보지만
**"이 권한이 이 워크로드에 과한가" 는 판단하지 않는다.**
과함을 판정하려면 실제 API 호출 이력과 비교해야 하고, 그것이 CIEM 영역이다.

IAM Access Analyzer 의 미사용 권한 분석이 이 역할을 하지만,
호출 이력이 쌓여야 동작한다. 생성 직후에는 판단할 근거가 없다.

## 두 표준이 모두 놓친 것

| # | 항목 | 왜 안 잡히는가 | 담당 영역 |
| --- | --- | --- | --- |
| 5 | 과도한 IAM 권한 | 설정이 아니라 적정성 판단이 필요 | CIEM |
| 6 | 인스턴스 내부 평문 비밀번호 | 클라우드 리소스 설정의 범위 밖 | CWPP / 시크릿 스캐닝 |

**이 둘이 공격 경로 A 의 양 끝이다.**

```markdown
[경로 A] 애플리케이션 SSRF
  → IMDSv1 호출 (#7)          ← FSBP EC2.8 로 탐지됨
  → 임시 자격증명 탈취
  → S3FullAccess 권한 (#5)     ← 어느 표준도 탐지 못 함
  → 계정 내 모든 버킷 접근
```

경로의 입구(#7)는 잡히고 출구(#5)는 안 잡힌다.
**CSPM 점수가 올라가도 이 경로는 그대로 남는다.**

## FSBP 는 탐지 도구의 활성화 여부도 점검한다

예상하지 못한 유형의 실패 항목이 있었다.

| 컨트롤 | 내용 |
| --- | --- |
| Inspector.1 / 2 / 4 | EC2, ECR, Lambda 스캔 활성화 |
| GuardDuty.7 / 11 / 12 / 13 | Runtime Monitoring (EKS, ECS, EC2) |
| Macie.1 | Macie 활성화 |

CSPM 이 **CWPP 가 켜져 있는지를 점검한다.** 설정 점검 도구가
워크로드 보호 도구의 부재를 위반으로 기록하는 구조다.

보안 통제는 개별 항목이 아니라 계층으로 평가된다는 것을 보여준다.

> 확인 필요: Inspector 를 전날 활성화했는데 Inspector.1 / 2 가 실패로
> 기록되어 있다. 측정 데이터가 활성화 이전 시점일 가능성과
> 활성화가 실제로 적용되지 않았을 가능성을 모두 확인해야 한다.

## 예측하지 못했는데 탐지된 항목

| 탐지 항목 | 심각도 | 원인 | 왜 예상하지 못했는가 |
| --- | --- | --- | --- |
| EC2.2 — 기본 보안그룹이 트래픽 허용 | 높음 | VPC 생성 시 자동 생성 | 내가 만들지 않은 리소스도 평가 대상 |
| EC2.6 — VPC 플로우 로깅 미설정 | 보통 | 내 VPC + 기본 VPC | 로깅을 CloudTrail 만 생각함 |
| EC2.10 / 55~60 — VPC 엔드포인트 미설정 | 보통 | 6 개 컨트롤 | 비용 항목으로만 알고 있었고 보안 기준인 줄 몰랐음 |
| RDS.5 — Multi-AZ 미구성 | 보통 | 단일 AZ 배포 | 가용성 항목이 보안 표준에 있을 줄 몰랐음 |
| RDS.23 — 기본 포트 사용 | 낮음 | 3306 그대로 사용 | 포트 변경이 통제 항목인 줄 몰랐음 |
| RDS.10 — IAM 인증 미구성 | 보통 | 비밀번호 인증만 사용 | 6 번의 근본 해법이 여기 있었음 |
| IAM.2 — 사용자에 정책 직접 연결 | 낮음 | Phase 0 에서 `lab-admin` 에 직접 부여 | 계정 준비 과정도 평가 대상 |
| Account.1 — 보안 연락처 미등록 | 보통 | 계정 기본값 | 계정 메타데이터도 점검 대상 |
| EC2.182 — EBS 스냅샷 퍼블릭 차단 | 높음 | 계정 기본값 | 스냅샷 공개 차단이라는 개념 자체를 몰랐음 |

**RDS.10 이 특히 의미 있다.** 평문 비밀번호 문제(#6)를
Secrets Manager 로 푸는 것만 생각했는데, RDS IAM 인증을 쓰면
**비밀번호 자체가 없어진다.** IAM 토큰으로 접속하므로 저장할 자격증명이
존재하지 않는다. Day 3 교정에서 이 방향을 검토한다.

## Day 3 교정 우선순위

노출, 권한 범위, 데이터 민감도 세 축으로 판단한 결과다.

| 순위 | 대상 | 근거 |
| --- | --- | --- |
| 1 | RDS 퍼블릭 액세스 + 3306 개방 (#2, #3) | 인터넷에서 데이터에 직접 도달. 경로 B 전체 |
| 2 | EC2 역할 권한 축소 (#5) | 어느 도구도 잡지 않음. 경로 A 의 피해 범위 결정 |
| 3 | IMDSv2 강제 (#7) | 경로 A 의 입구 차단 |
| 4 | S3 퍼블릭 차단 (#1) | 매우 중요 등급, 조치 비용 낮음 |
| 5 | 비밀번호 제거 (#6) | Secrets Manager 또는 RDS IAM 인증 |

**2 순위를 도구 점수가 아니라 공격 경로 분석으로 정했다.**
#5 는 고쳐도 Security Hub 점수가 1 점도 오르지 않는다.
점수만 보고 작업 순서를 정하면 가장 위험한 항목이 뒤로 밀린다.
